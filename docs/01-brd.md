## 1. Контекст и цель

**Проблема:**
Учебный проект для отработки навыков системного аналитика в условиях, приближённых к реальным: распределённая система с синхронным REST, асинхронной Kafka, реляционной и NoSQL БД, ролевой моделью и жизненным циклом заказа.

**Цель:**
Создать MVP мини-маркетплейса, где продавцы публикуют товары, покупатели оформляют заказы, система обрабатывает оплату асинхронно через события.

**In scope (MVP):**
- Регистрация/аутентификация пользователей (JWT)
- Управление товарами (seller)
- Каталог с поиском и фильтрами (buyer)
- Оформление заказов (buyer)
- Асинхронная обработка оплаты через Kafka
- Отзывы на товары
- Базовое уведомление (лог/mock)

**Out of scope (MVP):**
- Реальная интеграция с платёжным шлюзом (Payment — mock)
- Реальная доставка
- Мобильное приложение
- Рекомендательная система
- Полноценный админский UI (только API)

## 3. Бизнес-требования (BR)

| ID | Требование | Приоритет |
|---|---|---|
| BR-01 | Система должна позволять пользователям регистрироваться и входить | Must |
| BR-02 | Система должна разделять пользователей по ролям: buyer, seller, admin | Must |
| BR-03 | Продавцы должны иметь возможность публиковать и управлять товарами | Must |
| BR-04 | Покупатели должны иметь возможность просматривать каталог и искать товары | Must |
| BR-05 | Покупатели должны иметь возможность оформлять заказы из нескольких товаров | Must |
| BR-06 | Система должна асинхронно обрабатывать оплату заказа | Must |
| BR-07 | Покупатели должны иметь возможность оставить отзыв после доставки | Should |
| BR-08 | Система должна уведомлять пользователей о ключевых событиях | Should |
| BR-09 | Администратор должен иметь возможность блокировать пользователей и товары | Should |
| BR-10 | Система должна выдерживать пиковую нагрузку без потери заказов | Should |

## 4. Функциональные требования (FR)

### 4.1. Аутентификация и пользователи (Auth Module)

| ID | Требование | Приоритет |
|---|---|---|
| FR-AUTH-01 | Регистрация по email + пароль (мин. 8 символов, 1 цифра, 1 буква) | Must |
| FR-AUTH-02 | Логин по email + пароль, выдача access (15 мин) и refresh (7 дней) JWT | Must |
| FR-AUTH-03 | Refresh-токен хранится в Redis с TTL и ротацией при обновлении | Must |
| FR-AUTH-04 | Logout — инвалидация refresh-токена | Must |
| FR-AUTH-05 | Пароли хешируются BCrypt (cost ≥ 10) | Must |
| FR-AUTH-06 | Роль назначается при регистрации (buyer или seller), admin — только вручную | Must |
| FR-AUTH-07 | Эндпоинт `GET /me` возвращает профиль текущего пользователя | Must |

### 4.2. Каталог и товары (Catalog Module)

| ID | Требование | Приоритет |
|---|---|---|
| FR-CAT-01 | Seller может создать товар (name, description, price, category, attributes) | Must |
| FR-CAT-02 | Seller может редактировать/удалять только свои товары | Must |
| FR-CAT-03 | Товар имеет статус: draft / active / archived | Must |
| FR-CAT-04 | Buyer видит только active товары | Must |
| FR-CAT-05 | Список товаров с пагинацией, сортировкой, фильтром по категории и цене | Must |
| FR-CAT-06 | Полнотекстовый поиск по name и description | Should |
| FR-CAT-07 | Гибкие атрибуты товара (разные категории — разные поля) — хранятся в MongoDB | Must |
| FR-CAT-08 | Кэширование карточки товара в Redis (TTL 5 мин, инвалидация при обновлении) | Should |

### 4.3. Заказы (Order Module)

| ID | Требование | Приоритет |
|---|---|---|
| FR-ORD-01 | Buyer создаёт заказ из 1+ товаров | Must |
| FR-ORD-02 | Заказ фиксирует цену товара на момент оформления (price snapshot) | Must |
| FR-ORD-03 | Заказ имеет статусы: CREATED → PAID → SHIPPED → DELIVERED / CANCELLED | Must |
| FR-ORD-04 | При создании заказа публикуется событие `order.created` в Kafka | Must |
| FR-ORD-05 | При успешной оплате Order становится PAID (через событие `payment.succeeded`) | Must |
| FR-ORD-06 | При неуспешной оплате Order становится CANCELLED (через `payment.failed`) | Must |
| FR-ORD-07 | Buyer видит только свои заказы, seller — заказы со своими товарами | Must |
| FR-ORD-08 | POST /orders поддерживает Idempotency-Key | Should |
| FR-ORD-09 | Отмена заказа buyer'ом возможна только в статусе CREATED | Should |

### 4.4. Отзывы (Review Module)

| ID | Требование | Приоритет |
|---|---|---|
| FR-REV-01 | Buyer может оставить отзыв только на товар из DELIVERED заказа | Should |
| FR-REV-02 | Один buyer — один отзыв на товар | Should |
| FR-REV-03 | Отзыв: rating (1–5), text, created_at | Should |
| FR-REV-04 | Отзывы хранятся в MongoDB | Should |
| FR-REV-05 | При создании отзыва публикуется `review.created` | Should |

### 4.5. Уведомления (Notification Module — mock)

| ID | Требование | Приоритет |
|---|---|---|
| FR-NOT-01 | На `user.registered` — лог «Welcome {email}» | Should |
| FR-NOT-02 | На `order.created` — лог «Order {id} created» | Should |
| FR-NOT-03 | На `payment.succeeded` / `payment.failed` — лог | Should |
| FR-NOT-04 | Все уведомления — через consumer Kafka (mock, пишет в лог) | Should |

### 4.6. Администрирование

| ID | Требование | Приоритет |
|---|---|---|
| FR-ADM-01 | Admin может заблокировать пользователя | Should |
| FR-ADM-02 | Admin может архивировать товар | Should |
| FR-ADM-03 | Admin видит список всех заказов | Should |

## 5. Нефункциональные требования (NFR)

| ID | Категория | Требование |
|---|---|---|
| NFR-01 | Производительность | p95 latency REST ≤ 300 ms (без учёта Kafka) |
| NFR-02 | Производительность | Пропускная способность: 100 RPS на чтение каталога |
| NFR-03 | Масштабируемость | Горизонтальное масштабирование stateless API |
| NFR-04 | Надёжность | At-least-once доставка Kafka-событий |
| NFR-05 | Надёжность | Outbox Pattern: событие публикуется гарантированно после commit транзакции |
| NFR-06 | Надёжность | Идемпотентность POST /orders и consumer'ов |
| NFR-07 | Безопасность | JWT access 15 мин, refresh 7 дней, ротация |
| NFR-08 | Безопасность | Пароли — BCrypt, HTTPS, CORS whitelist |
| NFR-09 | Безопасность | Rate limiting: 100 req/min на IP, 10 req/min на /auth/login |
| NFR-10 | Наблюдаемость | Structured logging (Serilog → JSON) |
| NFR-11 | Наблюдаемость | OpenTelemetry traces (Jaeger) |
| NFR-12 | Сопровождаемость | Чистая архитектура, модульный монолит |
| NFR-13 | Совместимость | OpenAPI 3.0 для REST, JSON Schema для Kafka |
| NFR-14 | Данные | Postgres — 3НФ, Mongo — document model, Redis — TTL-кэш |
| NFR-15 | Восстановление | DLQ для «ядовитых» Kafka-сообщений |

## 6. Ограничения и допущения

**Ограничения:**
- Все сервисы запускаются локально в Docker Compose
- Один инстанс Kafka (KRaft), один Postgres, один Mongo, один Redis
- Payment Service — mock (эмуляция успеха/неуспеха по вероятности)

**Допущения:**
- Нет реальных платежей, доставки, email/SMS
- Один язык — русский/английский в API (i18n вне scope)
- Аутентификация — только email + пароль (OAuth вне scope)

## 8. Глоссарий

| Термин | Определение |
|---|---|
| Buyer | Пользователь, покупающий товары |
| Seller | Пользователь, публикующий товары |
| Order | Заказ, состоящий из одного или нескольких OrderItem |
| OrderItem | Позиция заказа: товар + количество + цена на момент оформления |
| Outbox | Таблица в Postgres для гарантированной публикации событий |
| Saga | Распределённая транзакция через хореографию событий |
| DLQ | Dead Letter Queue — очередь «ядовитых» сообщений |
| Idempotency Key | Заголовок для защиты от дублирования POST-запросов |
